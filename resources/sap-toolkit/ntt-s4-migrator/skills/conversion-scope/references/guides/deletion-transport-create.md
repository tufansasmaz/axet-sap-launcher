# Create the deletion transport for decommissioned custom objects

> **Why we do this:** Delete-candidate objects identified in the impact table have zero runtime usage across the full SCMON monitoring period. Deleting them before the migration reduces the ATC scope for subsequent runs, removes dead code from the codebase, and decreases transport size during the migration itself. The deletion transport is a structured, reversible (in development) way to remove these objects — with customer sign-off at each step. This guide covers how to create the deletion plan and the resulting transport.

## Prerequisites

- `exec-summary-customisation` complete: delete-candidate list agreed with customer
- `impact-table-walkthrough` complete: customer has signed off on delete-candidates (each row reviewed for RFC edge cases)
- ABAP developer with delete/transport rights on the development system
- Transport management (STMS) available

## Steps

1. **Review the deletion plan output**

   Open `./migration/output/deletion-plan.md`. This file (generated by `DeliverableGenerator`) lists:
   - Object Type and Object Name for each delete-candidate
   - SUSG last-used date (from the aggregation data)
   - Usage count (should be 0 for confirmed delete-candidates)
   - Any edge-case flags added during `impact-table-walkthrough` (e.g. "RFC-callable — cross-check inbound calls")

2. **Resolve all edge-case flags before proceeding**

   For any row flagged as "RFC-callable — cross-check inbound calls":
   - Run `SM59` on the source system to identify all RFC destinations pointing to this system
   - For each destination's source system, check if the flagged function module appears in the call log or ATC scope
   - If any inbound caller is found: remove the object from the delete-candidate list and reclassify as Advisory
   - Document the resolution in `./migration/LESSONS.md`

   WHY: SCMON only captures local calls. A function module that is never called locally but IS called from a remote system shows zero usage in SUSG. Deleting it would break the remote caller silently.

3. **Get written customer sign-off on the final delete list**

   Email the finalised deletion-plan.md to the customer's technical lead and project sponsor. Request written approval (email reply is sufficient).

   Do NOT create transports before receiving written sign-off. Accidental deletion of a live-but-unmonitored object is an incident.

4. **Create the deletion transport on the development system**

   On the development system, open `SE80` (Object Navigator) or use `SE38` / `SE24` / `SE37` as appropriate for each object type.

   For each confirmed delete-candidate:
   - Open the object
   - Select *Object* → *Delete* (or the equivalent delete function for the object type)
   - When prompted for a transport, use the same transport order for all objects: `DEV_DELETION_<SID>_<YYYYMM>`

   Alternatively, use transaction `SLIN` or a mass-deletion report if available in the customer's landscape. The exact tool depends on the object type mix — discuss with the ABAP lead.

   WHY: Grouping all deletions in one transport makes it easy to revert (reject the transport) if a late-discovered inbound caller surfaces.

5. **Test the deletion transport in Quality**

   After development deletion and transport release, import the transport to the Quality system.
   - Run regression tests on the business processes that previously referenced these objects (SAP Solution Manager or customer's test management tool)
   - Confirm: no short dumps, no missing program errors

   Only after Quality validation should the transport be scheduled for Production import.

6. **Schedule the Production import**

   Work with Basis to schedule the deletion transport import during a maintenance window. Avoid production-critical periods (month-end, quarter-end).

   Add the transport number to `PROJECT_PLAN.md` under "Deletion transport."

7. **Re-run ATC after deletion**

   After production import, trigger a new ATC run (return to `atc-run-execute`). The delete-candidate objects should no longer appear in findings. This confirms the scope reduction and provides an updated finding count for re-baselining the migration project.

8. **Record in PROGRESS.md**

   Append: "Deletion transport created: <transport ID>; objects deleted: <count>; Quality import: <date>; Production import: scheduled for <date>"

## Expected behaviour

- Deletion transport contains all confirmed delete-candidates and no false positives
- Quality import succeeds without ABAP dumps
- Customer written sign-off on file
- ATC re-run shows reduced finding count

## Common pitfalls

| Symptom | Likely cause | Fix |
|---|---|---|
| ABAP dump after Quality import | Object was called by an unmonitored system | Revert transport; return to edge-case review in Step 2 |
| Transport import rejected by STMS | Locked objects or conflicting transports | Unlock with Basis help; resolve conflicts; reimport |
| Customer refuses sign-off | Uncertainty about whether objects are truly unused | Return to `impact-table-walkthrough`; extend SCMON monitoring period if < 12 months |
| Finding count unchanged after ATC re-run | Deleted objects had duplicates in other packages | Investigate; the ATC findings point to a remaining copy |

## When to come back

Return here in a follow-up project phase when:
- A second round of delete-candidates is identified after a further 6-month monitoring extension
- Additional namespaces are added to scope
