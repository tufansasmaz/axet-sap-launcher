# Walk through the impact table with the customer project team

> **Why we do this:** The impact table (`output/impact-table.xlsx`) is the single artefact that translates raw ATC findings into business language: which custom objects need mandatory changes, which can be deleted, what effort is estimated, and what is the risk to go-live. Walking through it with the customer's technical leads and business owners converts a data dump into a shared understanding of what the migration will cost. Skipping this step leaves the exec summary unsupported and makes effort estimates contestable.

## Prerequisites

- Plugin's `analyze` run complete: `output/impact-table.xlsx` and `output/impact-table.md` generated
- `readiness-check-export` complete: RC tile data available for sizing and business-function context
- Customer technical lead and at least one business stakeholder available for the workshop
- `PROJECT_PLAN.md` updated with customer name, go-live target, and custom namespaces

## Steps

1. **Open the impact table**

   Open `./migration/output/impact-table.xlsx` in Excel or the customer's preferred tool.

   The table has the following column structure (generated by the plugin's `DeliverableGenerator`):
   - Object Type, Object Name, Package, Namespace
   - Impact Class (Mandatory / Advisory / Delete-candidate / No-action)
   - Priority (1/2/3 from ATC findings)
   - Effort Band (XS/S/M/L/XL — from `ImpactMapper`)
   - Usage Count (from SUSG/CCM data)
   - Last Used (month/year from SUSG aggregation)
   - SAP Note (primary simplification item Note)
   - Note Summary (plain-language text from `NoteSummariser`)
   - Remediation Hint (from Simplification Database)
   - Cluster (thematic grouping from `ImpactMapper`)

2. **Walk through Impact Class distribution**

   Start with a summary view: how many objects per Impact Class?
   - **Mandatory**: these must be addressed before go-live. No exceptions.
   - **Advisory**: strongly recommended; risk-score if deferred.
   - **Delete-candidate**: usage count = 0 for ≥12 months. Propose decommission.
   - **No-action**: either already compatible or out of scope.

   WHY: Impact Class is the primary triage axis. Start here, not with Priority numbers, which can mislead without usage context.

3. **Deep-dive on Priority-1 Mandatory objects**

   Filter: Impact Class = Mandatory AND Priority = 1.

   For each cluster:
   - Read the Note Summary aloud (plain language from `NoteSummariser`)
   - Show the Remediation Hint
   - Ask the customer: "Does this object/cluster belong to a specific business process? Who owns it?"
   - Estimate: is the Effort Band realistic for this customer's team?

   Document any customer corrections to Effort Bands directly in the XLSX (the plugin flags manual corrections as lessons in PROGRESS.md via the PostToolUse hook).

4. **Review Delete-candidates**

   Filter: Impact Class = Delete-candidate.

   For each entry:
   - Confirm: the object has zero usage for ≥12 months across all SCMON-monitored calls
   - Check: is the object RFC-callable from another system NOT monitored by SCMON? (Edge case — consultant must cross-check inbound RFC destinations)
   - Customer sign-off required: "Can this be deleted before go-live?"

   WHY: Deleting objects before migration reduces ATC scope, speeds future checks, and reduces transport risk. But the customer must own this decision.

5. **Identify the top 5 risk clusters**

   Ask `ImpactMapper` output to group findings by Cluster. With the customer, agree on the Top 5 clusters by combined Effort + Priority.

   Record in `PROJECT_PLAN.md` under "Top risk areas." These clusters feed the exec summary.

6. **Capture customer corrections and add-ons**

   For any row where the customer says "that's wrong" or "this object is actually not used":
   - Update the cell in the XLSX
   - Write a brief note in the Comments column
   - The PostToolUse hook captures this as a manual-correction lesson

7. **Export the validated impact table**

   Save the reviewed XLSX as `output/impact-table-reviewed-<date>.xlsx`. This is the customer-accepted version.

## Expected behaviour

- Workshop produces a customer-signed-off impact table
- Top-5 risk clusters identified and recorded
- Delete-candidate list reviewed and customer has agreed on decommission scope
- Any Effort Band corrections captured in the XLSX

## Common pitfalls

| Symptom | Likely cause | Fix |
|---|---|---|
| Customer disputes Effort Band estimates | ImpactMapper used insufficient Note body context | Download and re-ingest the disputed Note; re-run ImpactMapper for the cluster |
| Delete-candidates include RFC stubs | SCMON only monitored local calls; inbound RFCs not captured | Flag these rows; consultant must manually cross-check inbound RFC log |
| Too many Priority-1 findings to review in one session | Large custom codebase | Split workshop by business process / package; schedule follow-up |
| Note summaries too terse | Notes not pre-downloaded | Return to `note-download-batch`; download missing Notes; re-run analyse |

## When to come back

Return here after:
- A re-analysis (new ATC run with updated CCMSIDB) — compare delta to the previously reviewed table
- Customer proposes additional objects for deletion during the project

## Output for the next step

- Customer-reviewed `output/impact-table-reviewed-<date>.xlsx`
- Top-5 risk clusters (for `exec-summary-customisation`)
- Agreed delete-candidate list (for `deletion-transport-create`)
- Effort totals by Impact Class (for `jira-import-procedure` and exec summary)
