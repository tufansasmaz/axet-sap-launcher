# Node catalog

Property sets below are transcribed from a **real exported project** (an Okta-secured
LLM endpoint with a generated user-admin area, 29 nodes) and from the 6.5.2 user
manual. Where a value is a tenant detail it is shown as a placeholder — see
`scripts/scrub_flow.py`.

This file covers the nodes you build with. For the **other 58** — SharePoint, SQL,
NoSQL, Excel, session, the worker pool, Python and Node backends — and for which npm
module owns each type, see [`palette.md`](palette.md).

The rule that catches people: **`deptapps-*` and `axetflows-*` both exist.** The rename
is unfinished in the product. Never "fix" a `deptapps-` type in an existing flow, and
when you read a security context read both spellings.

## Structural

### `tab`
```json
{"id":"<16 hex>","type":"tab","label":"User Okta Entity","disabled":false,
 "info":"","env":[],"__deptAppsAssociatedEntity":"DeptappUserLoginOkta"}
```
`__deptAppsAssociatedEntity` marks a tab that the Flows Assistant generated for one
data entity (its forms, its CRUD wiring). Hand-built tabs do not have it. Leave it
alone — it is how the assistant finds the tab again.

### `global-config`
```json
{"id":"<16 hex>","type":"global-config","env":[],
 "modules":{"deptapps-flows-contrib-nodes-enabler":"2.2.9"}}
```
Declares the contrib modules the project depends on. If a flow you import needs the
enabler nodes and this is missing, the designer shows "missing nodes to install".

### `subflow` / `subflow:<id>`
A subflow definition plus instances. **A subflow cannot contain an instance of
itself.** Shared subflows arrive via Settings -> Palette -> Install -> Shared Subflows.

## Configuration nodes

Configuration nodes have **no `x`/`y` and no `wires`**. They may have no `z` at all
(global) and the designer lists them in the sidebar; unused ones are drawn dotted.
Other nodes reference them by id.

### `http-in-security-config`
```json
{"id":"<16 hex>","type":"http-in-security-config","name":"Okta",
 "public":false,"roles":["ROLE_ADMIN","ROLE_USER"]}
```
`public:false` is what makes an HTTP endpoint require a login. An endpoint that fronts
an LLM must not be public.

### `deptapps-app-auth-okta`
```json
{"id":"<16 hex>","type":"deptapps-app-auth-okta",
 "configurationName":"<your-auth-config-name>",
 "dbEngineType":"localStorage","databaseName":"<your-db-name>",
 "userField":"userId","roleField":"roles","autoConfigured":true,
 "defaults":false,"defaultProject":"","defaultModel":""}
```
`dbEngineType` is `"localStorage"` or `"noSQL"` and is **required** — an export taken
before the field existed does not have it, and copying that node forward is a live
trap. See `axetflows-app` below.
Generated by Flows Assistant -> Apply Auth App -> OKTA Authentication, together with a
user database, CRUD forms, a login config and an admin area. It carries **no secret**,
so it can equally be written straight into the JSON - see `axetflows-app` below, which
is where it matters. Basic Authentication is
the other option and seeds `admin/admin` — change it before anything leaves the
sandbox.

## App and UI

### `axetflows-app`
```json
{"id":"<16 hex>","type":"axetflows-app","z":"<tab>","name":"Securized App with Okta",
 "welcomePage":null,"sidebarMenuOrientation":"left","logoImage":"default",
 "schemeColor":"","customCSSErrors":0,"authConfig":"Okta",
 "sessionExpireTimeInMinutes":null,"basicInternalDb":"","oktaDb":"<auth config id>",
 "roles":"","__wellKnownRes":{},"x":140,"y":80,"wires":[]}
```
**Without an `app` node the project can only be deployed standalone; with one it can go
to the cloud; with one that uses OKTA it can go both ways** (user manual 6.5.2,
"Production Deployment"). House rule: every app carries the pair — a desktop build
without it is something the user has asked for, not a default. Ask.

**HTTP 500 `"Credentials is not well configured on App node"` has two causes, and both
live on the auth configuration rather than in your flow.** Either way the project
deploys, publishes and registers its route, then fails every single request in the
platform's own middleware before one node runs. A live NTT deployment hit both in
succession, and neither is visible in the export — each reads like a default.

1. **`authConfig:"Okta"` with `oktaDb:""`** — it points at no auth config node at all.
2. **`oktaDb` points at an auth node with no `dbEngineType`.** That field is declared
   `required: true` in the node's own registration, and an auth node lifted from an
   older wizard export predates it. This is the subtler one: the flow looks correct,
   the id resolves, and the error message says nothing about a missing field.

Fixing either does **not** require the designer wizard, which is worth knowing because
that is the advice everyone gives. The auth node holds no secret — its registration
declares no `credentials` block and the export's `credentials` array stays empty — so
it can simply be written into the JSON:

```json
{"id":"<16 hex>","type":"deptapps-app-auth-okta",
 "configurationName":"OKTA Authentication",
 "dbEngineType":"localStorage",
 "databaseName":"deptapp-user-login-okta",
 "userField":"userId","roleField":"roles",
 "autoConfigured":true,
 "defaults":false,"defaultProject":"","defaultModel":""}
```

`dbEngineType` is one of exactly two literals — `"localStorage"` or `"noSQL"` — and
`"localStorage"` is what goes with a `databaseName` the platform autogenerated.
`autoConfigured: true` is what the wizard's own code writes alongside it.

**What success looks like is a different error, not silence.** Verified live on
2026-09-01: adding those two fields turned the 500 into
`400 {"code": 30, "message": "Credentials are mandatory to access this resource."}` —
which is the *correct* answer to a call carrying no bearer token against a
`public:false` endpoint. Do not read that 400 as the same failure continuing; it is
the platform middleware finally reaching the auth check.

It is a **config node** — no `z`, no position, sitting beside the tab's nodes — and
`oktaDb` takes its id. `databaseName` points at the platform's autogenerated user
store (the db nodes that read it carry `dbNameIsBlockByAutogeneration: true`), so
there is nothing to create. Check the project can load the type first: it is
registered in the export's own `configData.nodes` under the name **`auth-okta`**,
whose `types` array is `["deptapps-app-auth-okta"]`. The siblings are
`auth-basic-internal`, `auth-azure-ad`, `auth-ldap`, `auth-cas` and `auth-openid`.

What the wizard adds beyond this is the *user administration* UI — two forms, four
`axetflows-db-*` nodes and its own app node — none of which an API-only flow needs,
and that second app node is a reason not to import its export wholesale.

**If you hand-edit, the bill of materials takes care of itself.**
`info.deptAppVersionInfo.usedNodes` is recomputed by the platform on import from what
the flow contains - a type you add is imported and the list grows to name it (measured
on the re-export of 1.0.2, 2026-09-03). An earlier version of this paragraph said the
import drops unlisted types; that was inferred, not measured, and is retracted. See
"What an import does to a version" in [`platform.md`](platform.md).

It also holds `menu` (a `root` -> `section` -> `page` tree, each page carrying `text`,
`icon` and `pageId`) and `customCSS`. `authConfig:"authNone"` and Basic exist on the
node and are not options here: every app authenticates with Okta, and
`validate_flow.py` refuses anything else.

**A form page that is not on this node's menu does not exist to the user.** Creating
the `axetflows-form` node wires the logic and nothing else — the page has no route into
the application until the app node's *Menu* tab gets an entry for it:
**Properties -> Menu -> Site Map -> Menu -> Add form view** (the sibling entry,
*Add section*, makes a group rather than a page). This is the single most common way a
correctly built page is reported as "not working".

When adding one, **add**: leave the existing pages and menu entries alone unless
replacing them was the request, and reuse the project's existing app node rather than
creating a second one.

### `axetflows-form`
The Form.io-backed page (formio 4.8.1 on Bootstrap 4 + SB Admin 2). Its outputs are
the form's actions in order — a search form typically has one output per button plus
one for the grid query and one for `onInitForm`. Read the wiring, not the count:
`inspect_flow.py` prints `(out N)` per branch.

**Submitted data arrives at `msg.payload.data.<key>`**, where `<key>` is the
component's *Property Name*, not its label. `msg.payload` also carries `metadata` and
`state`; the payload itself is not the form data.

Two rules about pages that are not obvious from the JSON:

- **`welcomePage` and `menu` DO survive a `.deptapp` import — write them into the file
  and skip the designer.** The tutorial says the opposite and it is describing the
  other path: a plain **flows JSON** export/import loses both, a **`.deptapp` version
  import** does not. Measured on 2026-09-02 by round-tripping one: a `menu` tree and a
  `welcomePage` set by hand came back from the platform byte-for-byte identical, form
  node and all. What does not happen by itself is the *deploy* — importing a version
  does not run it, so the app keeps serving the previous one and its old menu. An app
  that "ignored the menu we shipped" is almost always still running the version before
  it.
- **A menu entry finds its page by matching its label against the form node's `Name`,
  exactly and case-sensitively** — not by the `pageId` stored beside it. Rename a form
  node and its menu entry goes nowhere.
- **Adding a page grows `usedNodes`, and that list is a gate.** `axetflows-form` has to
  be on it or the form is dropped on import. The platform recomputes the list from what
  the flow actually uses and prunes it on the way back out (94 rows in, 12 rows back),
  so borrowing a wide registry from another export is a safe way in — it does not stay
  wide.

A `file` component needs **Storage = `base64`**, the only mode that works without a
separate storage backend. Each uploaded file then arrives as
`{name, originalName, type, size, url: "data:<mime>;base64,<...>"}` — the content is in
`url`, nothing is written to disk, and the upload is ~33% larger on the wire. The
`File` component itself sits under **Premium** in the component palette.

Custom CSS goes on the **app** node (Style -> Custom CSS) and targets
`.formio-component-<key>`, again the Property Name. CSS cannot remove part of a text
node — hide the original and rewrite it with `::after`.

### `axetflows-view-action`
```json
{"id":"<16 hex>","type":"axetflows-view-action","z":"<tab>",
 "name":"refresh_current_page","action":"update","redirectPage":null,
 "downloadFile":false,"fileName":"","inputType":"buffer",
 "message":null,"messageType":"info"}
```
`action` is `redirect` (with `redirectPage` = the target form node id) or `update`
(refresh the current page). It also delivers a toast (`message`, `messageType`) and a
file download (`downloadFile`, `fileName`, `inputType`).

**`rx-view-action` is the other one.** It pushes a view update over WebSocket without
the user pressing anything; `view-action` needs a user-initiated action. If a screen
must change on its own — a long job finishing — you need `rx-view-action`.

### aXet UI / SPA App node
Deploys a compiled SPA (React, Angular, Vue, Vite) as the project's front end, in place
of the form pages.

## Persistence

All four share `dbName`, `dbNameIsBlockByAutogeneration` (true when the Flows Assistant
owns the database name), and a `property`/`propertyType` pair naming where on `msg` the
data lives.

| type | key properties |
|---|---|
| `axetflows-db-persist` | `property` (`submission`), `propertyType` (`msg`) |
| `axetflows-db-find-one` | `identifierProperty` (`_id`), `bindingProperty` (`onInitSubmission`) |
| `axetflows-db-remove` | `property` (`_id`) |
| `axetflows-db-query` | `searchFilterProperty`, `bindingProperty`, `sort`/`sortProperty`, `paginator` + `pageNumberProperty` / `itemsPerPageProperty` / `totalItemsCountProperty` |

Databases are **encrypted per project**. That is why the only supported transfer route
is Flows Assistant -> Import/Export LocalStorage, and why you cannot read a project's DB
from outside it. `XLSX to LocalStorage` creates one DB per sheet. `Migrate to ext.
database` moves it to MongoDB or Cassandra.

`SQL Engine`'s `sql-query` node has no settings at all — the help text promises every
flow its own cloud database. That database still has to be **provisioned on the
platform side**, and until it is, every query fails:

```
No database password found for flowId: 25708 in environment: dev.
Check Key Vault secret 'flow-context-database-sql-dev-25708'
```

This is not fixable in the node. Ask the platform team. Until then, a JSONL file under
`/internal-storage-files/` is the drop-in substitute — see `references/delivery.md`.

**`sql-query` interpolates with Mustache, and that is string concatenation, not
parameter binding.** `'{{payload.name}}'` is textually replaced. A value that came
from a user is a SQL injection. Pass numbers through `parseInt` and double the single
quotes in text before it reaches the query.

## AI

### `axet-agents-execute` — "Flows AI Agent" (palette **aXet AI**)

The current agent node, and the one to reach for. Not the same thing as
`enabler-llm`, which is a raw chat-completions call.

```json
{"id":"<16 hex>","type":"axet-agents-execute","z":"<tab>","name":"3. TS Reviewer",
 "agentId":"","agentName":"","description":"3. TS Reviewer",
 "instructions":"Sen titiz bir SAP teknik lideri sin. ...",
 "model":"aws-anthropic/eu.anthropic.claude-sonnet-5","input":"",
 "mcpTools":"[]","coreTools":"","customTools":"[]",
 "temperature":0.3,"maxRetries":2,"maxSteps":15,"timeout":300000,"stream":false,
 "outputSchema":"","projectId":"<your-project-id>",
 "x":420,"y":480,"wires":[["<ok>"],["<error>"]]}
```

- **Input** is `msg.payload` as plain text. **Output** is `msg.payload.response`.
- **Two outputs**: success, then error. The error branch carries
  `msg.error = {message, code, details}`. Leaving it unwired hides every model and
  gateway failure — `validate_flow.py` warns about it.
- **`projectId` and `model` are two separate mandatory fields.** An empty one is not
  a deploy error; it is a run-time error. Blank `agentId` means *ephemeral* mode (the
  node carries its own instructions); filling it binds a registered agent.
- **Pick both dropdowns with the mouse.** Keyboard selection renders the label and
  does **not** persist `projectId`. The lists also load late — a field that looks
  blank may still be fetching, so trust the run-time error, not the dialog.
- `model` is `provider/model`: `ntt/gpt-5.4-mini`,
  `aws-anthropic/eu.anthropic.claude-sonnet-5`. Budget is per project and may be per
  provider. `Fallbacks = None` means exactly that — no automatic failover.
- `timeout` is 300000 ms. It is **not** the only clock: the Azure gateway in front of
  the model has its own, and a long conversation dies with `OriginTimeout` well
  before the node gives up. Feedback loops must pass **summaries, not full text**.
- The debug panel truncates the error. The full chain — Mastra -> litellm -> provider
  — is in `docker logs <container>`.

**`outputSchema` is the field that makes agents composable.** It is a JSON Schema
string; with it the agent returns a typed object instead of prose, and a `switch` can
branch on a field:

```json
"outputSchema": "{\"type\":\"object\",\"properties\":{\"approved\":{\"type\":\"boolean\"},\"findings\":{\"type\":\"array\",\"items\":{\"type\":\"object\",\"properties\":{\"item\":{\"type\":\"string\"},\"severity\":{\"type\":\"string\"}}}},\"summary\":{\"type\":\"string\"}},\"required\":[\"approved\",\"summary\"]}"
```

Set it on the **Input/Output** tab (Simple / Advanced JSON / Validate). Without it,
one agent's answer cannot drive another node except by string matching.

**The Tools tab - `mcpTools`, `coreTools`, `customTools` - is real and undocumented.**
All three ship on the node as strings (`"mcpTools": "[]"`), and consultants do ask
about them: the question that reached us on 2026-09-08 was whether an agent can reach
SharePoint or Outlook through an MCP connector listed there. What can be said honestly:

- The fields exist. Something is meant to go in them.
- **No aXet documentation describes them.** "MCP" and "Model Context Protocol" appear
  **zero** times across all eight official PDFs held on 2026-09-08 - 205 pages, the
  complete 6.5.2 user manual among them. Not a thin section; nothing at all.
- No export captured so far has a populated one. The full-palette export's agent node
  carries `""` in all three, so there is no example to copy either.
- The lists are almost certainly scoped to `projectId`, like the model and agent
  dropdowns beside them. A connector a colleague can see on their project is not
  evidence it exists on yours.

So do not write these fields by hand and do not promise a consultant they work. Open
the node's **Tools** tab in the designer and read what the list actually offers - that
is a one-minute check and it is the only authority there is. If it turns out to be
populated, capture an export and this paragraph gets replaced by a schema.

**For SharePoint and Outlook there is a documented route that needs none of this**, and
it is the one to reach for first: the `MS Graph Sharepoint` and `MS Graph Mail` palette
categories (manual 6.5.2 p21, field lists in [`palette.md`](palette.md)). Put the Graph
node **in front of** the agent and hand the content over in `msg.payload`:

```
[ms-graph-shp-download-file] -> [function: build prompt] -> [axet-agents-execute] -> [ms-graph-mail-send]
                                                                  |
                                                                (err) -> [catch]
```

That shape also survives the audit better than a tool called from inside an agent:
each action is a node the auditor can see wired to its `use-case` node, and a tool
invocation hidden in an agent's own loop is not.

> **A node literally named `aXet Agent` sits in the `Deprecated Nodes` palette.**
> It is not this node. Do not use it, and do not "fix" a flow by swapping to it.

### `enabler-llm`
```json
{"id":"<16 hex>","type":"enabler-llm","z":"<tab>","name":"",
 "model":"gpt-4.1","slug":"<your-slug>","projectid":"<your-project-id>"}
```
**Input is `msg.messages`** — `[{role, content}, ...]` — set by the Function node in
front of it, not `msg.payload`. It is a **top-level `msg` property**, and getting this
wrong is expensive precisely because nothing complains: a flow that builds the list into
`msg.payload` passes validation, deploys, publishes, answers 200, and sends the model
nothing. Our own shipped template had this defect until 2026-09-01. Output `msg.payload`
follows the OpenAI chat shape,
`msg.payload.choices[0].message.content`. **Never let that shape reach your callers**;
map it to your own contract in a Function node right after.

`slug` and `projectid` are tenant configuration. Get them from your own project. Left
unset, the node falls back to the project and model chosen during node activation —
convenient in design, and a surprise in an environment where activation chose
differently.

**`model` is not an OpenAI-only field.** A deployed NTT gateway runs an Anthropic
model id (`eu.anthropic.claude-sonnet-5`) against a `slug` naming the provider route —
the slug picks the route, and the model id is that provider's own, region prefix
included.
The *response* still arrives in the OpenAI chat shape whatever the provider, which is
exactly why the mapping Function node in front of your callers is not optional: change
the provider and the caller must not notice.

**Everything else the node takes, it takes off `msg`, and none of it is in the editor
panel.** Read `nodes/llm/llm.js` in `deptapps-flows-contrib-nodes-enabler` rather than
inferring from what the panel shows — the properties above are what a *designer* can
set, not what the node reads.

```javascript
const DEFAULTS = { n: 1, max_tokens: 50, temperature: 0.7, top_p: 1.0 };
```

| `msg` property | effect | default if unset |
|---|---|---|
| `msg.model` | model for this request — **outranks the node's own `model`** | node's `model`, then the security context, then a constant |
| `msg.slug` | provider route — outranks the node's `slug` | node's `slug` |
| `msg.max_tokens` | length cap | **50** |
| `msg.temperature` | 0–2, rejected outside the range | 0.7 |
| `msg.top_p` | 0–1 | 1.0 |
| `msg.n` | completions returned | 1 |
| `msg.query` | a plain string, wrapped in a default system message | — use instead of `msg.messages` |

**`max_tokens` defaults to 50, and that is the answer to "why does every reply stop
mid-sentence".** It is a node default, not a project or tenant cap; set `msg.max_tokens`
in the Function node in front and it goes away. This was written up here and in the
gateway walkthrough as a project-level limit with no flow-side fix, which was wrong —
inferred from the node's missing `maxTokens` property instead of read off its source.

`msg.model` outranking the node is what makes a **per-request model picker** possible.
An unknown name is refused with `msg.model must be a valid model!`, never silently
substituted. You cannot enumerate the valid names from a flow or a browser: the
backend call behind `isValidModel` authenticates with
`process.env.DEPTAPPS_WEB_BACKEND_JWT_TOKEN`, and a Function node has no `process`. Any
picker is therefore a curated list plus free text.

After a successful call the node pushes the assistant's reply onto the messages array
and reassigns `msg.messages`, so a flow that loops back gets accumulated history
without rebuilding it.

Unlike the agent node, `enabler-llm` has **one** output — the observed deployment
wires it straight into the mapping function. A provider or gateway failure therefore
does not come back on a second wire; it raises, and a **`catch` node on the tab** is
what turns it into a 502 instead of a hung request.

### Python Agent node (aXet Python palette)
Runs LangChain / LangGraph / CrewAI / AutoGen agents, and is the execution boundary for
anything that has to pause for a human. Its dependencies are installed by the **Install
Dependencies** node (tutorials palette), or by the node's own **Auto Install**.

The entrypoint file defines one of `run(msg)`, `main(msg)`, `process(msg)` or
`handle_message(msg, node_id)`, and returns a serialisable dict. Settings that matter:
**Environment** = *UV (managed)* for an isolated runtime (Python 3.10-3.13),
**Dedicated Env** when it must not share dependencies with another python-agent,
**Timeout and memory** so a stuck run does not hold resources, and **API Gateway** only
when the Python app must expose FastAPI HTTP handlers — an internal flow does not need
it.

A long agent run must not block inside Python. Return a status the flow can branch on
and let Node-RED route the wait: `references/human_review.md`.

### Backend node (aXet Node js palette)
Two modes: **Handler** (a function invoked by the flow) and **Server** (a long-running
listener).

## Audit

Two nodes, both from `deptapps-flows-contrib-nodes-audit` (2.2.5 on 6.5.2). Together
they are the **Audit Status** deployment gate — no approval, no deploy, cloud or
standalone.

### `use-case`
```json
{"id":"<16 hex>","type":"use-case","z":"<tab>","name":"Audit LLM Call",
 "config":"<audit-config id>","userid":"<okta user id>",
 "projectid":"<your-project-id>","useCaseCategory":"<registered category>",
 "usecaseid":"<registered use case id>","isAI":true,"x":760,"y":200,"wires":[[]]}
```

Five things about it are easy to get wrong and all five fail the audit:

- **The Use Case field must be filled with a use case registered on the project.**
  Use cases are chosen from Category / Use case dropdowns when the development
  project is created, and the node's editor lists those same ones. The audit checks
  that the registered use cases are the ones the flows inform, so an invented id
  reads as an unfilled field. One project carried `UC-LLM-ENABLER-001` / `AUDIT`
  from its first version and was told exactly that (2026-09-03). Pick it in the
  designer once, export, copy the values from there; a fresh palette node ships with
  every field `""`, including `isAI`.

- **One per action, not one per flow.** A flow that reads a JIRA task *and* writes an
  Excel file needs two. `config` may be shared; the declaration may not.
- **It must be wired to the action it describes.** The auditor reads the wiring, so a
  node parked on an empty patch of canvas declares nothing. In the deployed gateway it
  hangs off the mapping function, downstream of the model call it is declaring.
- **`isAI: true` is the Generative AI tick**, and it is the *only* machine-readable AI
  declaration in the file — the `.deptapp` manifest's `hasAI` is null even for
  `enabler-llm`. Declaring a Generative AI use case as an ordinary one is precisely the
  unregistered use the audit exists to catch.
- **`userid` is a person**, the Okta id of whoever declared it. Scrub it before the
  export leaves the project.

`useCaseCategory` and `usecaseid` come from the registered use case, not from you —
take them from the audit entry rather than inventing a plausible-looking id.

### `audit-config`
```json
{"id":"<16 hex>","type":"audit-config","name":"Audit Credentials",
 "credentialname":"AuthType=Delegated;TenantId=<guid>;ClientId=<guid>"}
```
A configuration node — no canvas position, referenced by id from every `use-case`
node. `credentialname` carries tenant and client ids; it is tenant configuration and a
scrub target.

An approval **expires after 6 months**. Note the date at handover: nothing warns you,
and the next deployment is simply refused.

## Delivery

### `json-to-excel` (palette **Excel Utils**)

```json
{"id":"<16 hex>","type":"json-to-excel","z":"<tab>","name":"build workbook",
 "kind":"auto","bufferProp":"payload","payloadProp":"payload"}
```

Input contract is entirely in `msg.payload.data`: one key per **sheet**, each an array
of row objects, row keys becoming columns. Output is an `.xlsx` **Buffer** on
`msg.payload`. Styling comes from `xlsx-populate`, not from this node. Full rules and
the traps: `references/delivery.md`.

### `secret` (palette **credentials**)

```json
{"id":"<16 hex>","type":"secret","z":"<tab>","name":"recipients",
 "property":"recipients","propertyType":"msg"}
```

Writes a configured value onto `msg.<property>` and keeps it **out of `flows.json`** —
it lives in Node-RED's credentials store, so the export and the git repo stay clean.
The right home for a recipient list, an endpoint, an account name.

**It is not a vault.** Anyone with an editor session on the project can read it. It
keeps secrets out of version control; it does not keep them from colleagues.

### `ms-graph-mail-config` + `ms-graph-mail-send`

```json
{"id":"<16 hex>","type":"ms-graph-mail-config","name":"delegated mail",
 "authType":"DELEGATED","optionalScopes":"no",
 "fromMail":"<your-corporate-address>","tenant":"<selected from the dropdown>"}

{"id":"<16 hex>","type":"ms-graph-mail-send","z":"<tab>","name":"send",
 "config":"<config id>","to":"","subject":"","saveToSentItems":true}
```

`DELEGATED` needs no Azure AD app registration; `MANUAL` needs
`clientId` + `tenantId` + `clientSecret`.

**`fromMail` and `tenant` are not in `defaults`, and both are mandatory anyway.** Blank
`fromMail` makes both nodes `valid: false` and puts a warning triangle on the canvas;
blank `tenant` deploys cleanly and fails at run time with *"Please select the tenant
within your config node…"*. The dropdown fills dynamically — open the node, wait, then
select.

`DELEGATED` also requires the account to hold MS Graph Mail permission on the platform
side. Without it the node returns `An error occurred trying to retrieve the token.`
and there is nothing to configure your way out of — that is an IT request. The plain
SMTP `e-mail` node in the `email` palette is the fallback.

The whole message goes in `msg.payload` — subject, `toRecipients`, `body`,
`attachments`. See `references/delivery.md` for the shape.

## Stock Node-RED nodes in use

`http in` (`url`, `method`, `upload`, `skipBodyParsing`, `securityConfig`),
`http response`, `function`, `debug`, `comment`, `change`, `inject`, `switch`,
`catch`, `status`, `join`, `delay`, `link`, `file`, `file in`, `http request`.
They behave exactly as in Node-RED. Five of them have a field that decides whether the
flow works, and none of the five reports itself:

### `inject` — emit all four timing fields

```json
{"id":"<16 hex>","type":"inject","z":"<tab>","name":"run manually",
 "props":[{"p":"payload"}],"payload":"","payloadType":"date",
 "repeat":"","crontab":"","once":false,"onceDelay":0.1,
 "x":200,"y":200,"wires":[["<next>"]]}
```

**`repeat`, `crontab`, `once`, `onceDelay` must all be present**, even when empty. Omit
one and the designer reconstructs Repeat as `interval` with an empty period: the node
becomes invalid, never fires, and says nothing. The export always writes them, so this
only bites hand-built JSON — which is exactly what this skill produces.
`validate_flow.py` fails on it.

Scheduling uses `crontab` with Repeat = *at a specific time*: `30 7 * * 1-5` is 07:30
Monday to Friday. Extra entries in `props` set fields on the message without touching
the payload — useful for tagging which trigger fired.

### `http request` — Return must be a parsed JSON object

```json
{"type":"http request","method":"GET","ret":"obj","url":"https://...","senderr":false}
```

`ret` is `txt` by default. With `txt`, `msg.payload` is a **string**, and a downstream
`switch` on `payload.completed` matches nothing and drops every message. The debug
panel's type label (`string[83]` vs `Object`) tells you which you have — trust it over
the content, which looks identical.

### `switch` — always add `otherwise`

`checkall:"false"` stops at the first matching rule. A message matching **no** rule is
discarded silently: no error, no debug line, nothing on the canvas. Add a final rule
with `"t":"else"` wired to a debug or a log, or accept that some of your messages are
disappearing without trace.

### `file` — encoding decides whether a binary file survives

```json
{"type":"file","filename":"/internal-storage-files/report/out.txt","filenameType":"str",
 "appendNewline":true,"createDir":true,"overwriteFile":"false","encoding":"utf8"}
```

`overwriteFile:"false"` with `appendNewline:true` is the append mode used for logs and
JSONL. For a **Buffer** — an `.xlsx`, a PDF — `encoding` must be **`none`**, or the
buffer is stringified and the file is corrupt.

Paths matter more than they look: see `references/runtime.md`. Short version, only
`/internal-storage-files/` and `/external-repository-files/` survive the container.

### `catch` and `status`

`catch` is **tab-scoped**, has no input, and only sees `node.error(text, msg)` — the
one-argument form never reaches it. Nodes with their own error output (the AI agent)
bypass it entirely. `status` catches `node.status({...})` badge changes, which are
visual only and send no message of their own.

```json
{"id":"<16 hex>","type":"http in","z":"<tab>","name":"","url":"api/llm-enabler/v2",
 "method":"post","upload":false,"skipBodyParsing":false,"swaggerDoc":"",
 "securityConfig":"<security config id>","x":180,"y":280,"wires":[["<next>"]]}
```

`url` is relative. The full address exists only after publication:
`https://axet.nttdata.com/flows/cloud/<app-name>/api/llm-enabler/v2`.
